## 2. As três frentes

### 2.1 Frente B — o agendador (rebatizada de prioridade, ver seção 3)

**B1 confirmado, com dado pior que o do PR #10.** O PR #10 media "2 de 5 slots
entregues em um dia". Agora meço **zero entregas agendadas em ~19 horas**,
para os dois workflows (`consolidate.yml` e `operational-health.yml`), ambos
com a mesma cadência de silêncio a partir do mesmo horário (~18:52–19:44 UTC
de 2026-09-04). O padrão idêntico nos dois workflows aponta para falha de
entrega do `schedule:` do GitHub Actions neste repositório, não para um bug
específico de cada job — `workflow_dispatch` funcionou normalmente nesse
mesmo intervalo (rodei consolidações manuais com sucesso).

**Achado novo, não estava em nenhum documento: a vigilância está cega para
essa parada específica, agora, e eu sei exatamente por quê.**

`operational_health@2` mede `canonicalWindowsLast24h` contando **janelas
distintas por `ends_at`**, não execuções novas (comentário no próprio código:
"reprocessar a mesma janela não pode parecer entrega de slot" —
`supabase/functions/operational-health/index.ts:74-76`). A intenção era boa:
impedir que reprocessar a mesma janela repetidamente infle a contagem. Mas ela
não distingue "janela nova, processada agora" de "janela antiga, reprocessada
agora" — e ontem, dentro da etapa 3, eu reprocessei 8 janelas canônicas
distintas (`docs/AI-HANDOFF.md`, seção "Etapa 3") num intervalo de poucos
segundos, todas com `completed_at` de ontem à noite. Isso ainda está dentro do
período de 24h da medição de agora, então `canonicalWindowsLast24h=8`,
folgadamente acima do limite de 4 (`6 esperados − 2 de tolerância`). O
guardrail conclui "entrega normal" olhando para 8 janelas que, na verdade, são
6 antigas reprocessadas manualmente por mim mais 2 que já existiam — **nenhuma
delas é um slot novo entregue pelo agendador desde a parada.**

Reproduzi isso rodando `evaluateOperationalHealth` localmente com o snapshot
atual da função: `healthy: true`, `problems: []`, mesmo com o agendador parado
verificado há ~19h. Isso não é hipótese — é o mesmo código de produção,
alimentado com o dado real de agora.

Um segundo fator mascara o mesmo problema por outro ângulo:
`lastProcessingCompletedAt` mostra 8 minutos atrás porque **alguém da equipe
clicou em atualizar manualmente** hoje (`manual_refresh` às 14:24 UTC) — o que
é o comportamento correto do botão de atualizar do PR #6, mas faz a
consolidação parecer fresca quando na verdade é o caminho manual cobrindo,
sem querer, a ausência do automático.

**B2 — pg_cron.** `pg_cron` e `pg_net` estão disponíveis no projeto
(`default_version` presente, `installed_version` nulo) — instaláveis sem
contato com suporte. `supabase_vault` já está instalado, então a credencial de
processamento poderia viver lá em vez de em GitHub Secrets, acessível a uma
function `plpgsql` que a lê e chama `net.http_post` para a Edge Function. Não
tentei desenhar o SQL exato — isso é trabalho de implementação, não de
pesquisa.

**B3 — risco de falha silenciosa do pg_cron.** O prompt original pediu para eu
avaliar isso, e a seção 2.1 acima já é a resposta em miniatura: **qualquer
guardrail que meça "aconteceu algo recentemente" sem distinguir novo de
reprocessado é vulnerável ao mesmo tipo de mascaramento**, dentro ou fora do

Ver seção 6.

**A4 — a pergunta crítica do prompt original, e a resposta tem uma reviravolta
que muda o desenho da etapa 4.**

Fui verificar se trocar a fonte de identidade no sensor criaria um espaço de
identidade novo que duplicaria os 8 grupos recém-consolidados. A resposta é
mais estrutural do que eu esperava: **hoje, o `conversation_id` que o sensor
envia já não importa para a resolução de grupo, para nenhum evento que tenha
`conversation_label` não vazio.**

A cadeia de código, com arquivo e linha:

1. `process-window` chama `canonicalizeConversationEvent` **antes** de
   resolver (`supabase/functions/process-window/index.ts:47`);
2. essa função **sobrescreve incondicionalmente** `conversation_id` com
   `label:<rótulo canônico em minúsculas>`, descartando qualquer id que o
   sensor tenha enviado (`supabase/functions/_shared/canonical-conversations.js:16-26`):
   ```js
   export const canonicalizeConversationEvent = (event) => {
     const label = canonicalConversationLabel(event?.conversation_label);
     if (!label) return event;
     return { ...event, conversation_id: `label:${label.toLocaleLowerCase("pt-BR")}`, conversation_label: label };
   };
   ```
3. a chave de resolução usada por `buildGroupObservations`
   (`supabase/functions/_shared/group-resolution.js:12`) é
   `[source, sourceConversationId, normalizedLabel].join(":")` — e como
   `sourceConversationId` já é `label:<rótulo>`, essa chave colapsa para
   **uma função do texto do rótulo, e só dele**;
4. a RPC `resolve_group_observations` casa alias por
   `(network_id, source, source_conversation_id, normalized_label)`
   (`supabase/migrations/20260831190000_group_registry_foundation.sql:282-288`)
   — mesma conclusão no banco.

**Consequência prática, verificada e não hipotética:** se a etapa 4 apenas
trocar o hash do título por `getShortcutId()` no sensor, **isso não muda nada
na resolução de grupo hoje**, porque o valor que o sensor envia é descartado
antes de chegar à resolução. O `shortcutId` só passaria a ter efeito se o
pipeline de canonicalização/resolução for **também** alterado para preferir
um id estável do sensor quando presente, em vez de sempre recalcular a partir
do rótulo. Isso não estava explícito em `docs/GROUP-IDENTITY-PLAN.md`, que
descreve a mudança como só do lado do sensor.

Isso é, na verdade, uma boa notícia de segurança: **a etapa 4, do jeito que
está escrita hoje, não teria como criar um espaço de identidade novo e
duplicar os 8 grupos** — porque ela não teria efeito nenhum sem uma mudança
correspondente no backend. Mas também significa que o plano descrito na etapa
4 está incompleto: ela precisa de duas metades coordenadas (sensor **e**
backend), não uma.

Isso também expõe, com evidência de código e não só de teoria, o motivo pelo
qual D14 continua real: a identidade de grupo hoje é **inteiramente** o texto
do rótulo canonicalizado. Renomear um grupo no WhatsApp muda o rótulo, muda a
chave `label:<rótulo>`, cria um alias novo com `resolution_status` a
determinar (`created=true` na RPC) — e, dependendo da política de resolução
para "fontes múltiplas" (não auditei essa parte da RPC nesta sessão —
**NÃO VERIFICADO**), possivelmente um grupo novo.

## 2.4 Achado à parte — uma lacuna no processo de deploy, não no código

Ao investigar por que 8 aliases com prefixo `wa_` (o padrão antigo, volátil)
foram criados **depois** do horário em que a etapa 1 foi mesclada em `main`
(`fix/identidade-canonica-na-resolucao`, PR #9, mesclado
2026-09-04T03:35:42Z), encontrei a causa: **as Edge Functions
`process-window` e `process-latest-window` só foram efetivamente implantadas
às 2026-09-04T18:18:37Z** — quase 15 horas depois do merge. Confirmado
comparando o `updated_at` das duas funções (`list_edge_functions`) com os
`created_at` dos 8 aliases voláteis, que caem exatamente nesse intervalo
(entre 00:45 e 14:07 UTC de 2026-09-04), processados por execuções canônicas
às 07:47 e 14:51 — ambas antes do deploy real.

Isto não é um defeito de código: o merge para `main` neste repositório **não
implanta Edge Functions automaticamente**; implantação é um passo manual
(`supabase functions deploy`, rodado por um agente numa sessão anterior). Para
qualquer mudança que toque resolução de grupo — e a etapa 4 toca — esse
intervalo entre merge e deploy é uma janela real onde o comportamento antigo
continua ativo em produção mesmo com o código correto já em `main`. Vale
considerar um passo de CI que implante automaticamente após merge em `main`,
ou pelo menos um checklist que torne o deploy parte inseparável do "PR
mesclado" — ver pergunta 6.4.

## 4. Plano de execução detalhado — Frente B (primeira etapa)

Escopo: parar de confiar cegamente no `schedule:` do GitHub Actions e fechar o
ponto cego do guardrail. Dividido em duas partes independentes, na ordem em
que reduzem risco mais rápido por menos esforço.

### 4.1 Corrigir o guardrail primeiro (menor risco, maior valor imediato)

Arquivo: `supabase/functions/operational-health/index.ts`.

Hoje `canonicalWindowsLast24h` conta janelas distintas por `ends_at` dentro de
`processing_runs` com `completed_at >= 24h atrás`, sem olhar quando a própria
janela **deveria** ter sido processada. Proposta: além dessa contagem
(mantê-la, é útil), adicionar uma medida de **frescor do slot mais recente**:
`ends_at` do `canonical_slot` mais recente, comparado a `now()`. Se a
diferença exceder o intervalo entre slots (5h, `CONSOLIDATION_WINDOW_HOURS`
não muda, mas o espaçamento entre `CONSOLIDATION_LOCAL_HOURS` é de até 5h) por
mais que a tolerância já usada em outros lugares do código (30 min, ver a
política de comparação `same_slot_previous_day@1`), acender um problema novo,
por exemplo `scheduler_stalled`, independente de quantas janelas antigas foram
reprocessadas manualmente no mesmo período.

- arquivo a tocar: `supabase/functions/operational-health/index.ts` (query
  adicional: `select ends_at from processing_runs where window_kind =
  'canonical_slot' order by ends_at desc limit 1`, sem filtro de
  `completed_at`, para pegar a janela mais recente **por conteúdo**, não por
  quando foi processada);
- lógica de avaliação: `packages/supabase-core/src/operational-health.js`
  (mesmo padrão dos outros `problems`, com evidência e ação sugerida);
- teste a escrever: um caso onde `canonicalWindowsLast24h` está alto (many
  reprocessed) mas o `ends_at` mais recente é antigo — deve reportar
  `scheduler_stalled` mesmo assim. Este é exatamente o cenário real de agora;
  não é um teste hipotético, é o replay do que encontrei;
- como validar em produção: chamar a função e confirmar que ela **agora**
  reporta o problema que o estado atual do banco genuinamente tem. Se
  reportar `healthy: true` de novo, o teste não capturou o caso real;
- como reverter: redeploy da versão anterior da função (v4, hash
  `3e0c8be0035476bed34f5e2650b3a0c9933756040ee15e0812a2ab33a50385c4`, já
  registrado em `list_edge_functions`).

### 4.2 Decidir e implementar a fonte do agendamento

Isto é parcialmente uma decisão do Gabriel (pergunta 6.1), mas o desenho
técnico de cada opção pode ser preparado antes da decisão:

**Opção pg_cron** — dentro do Supabase, chamando a Edge Function via
`pg_net.http_post`, com a credencial de processamento em `supabase_vault` em
vez de GitHub Secrets. Elimina a dependência do `schedule:` do GitHub Actions,
que é a peça comprovadamente não confiável agora. Precisa de: instalar
`pg_cron` e `pg_net` (migration aditiva), uma função que leia o segredo do
Vault e chame a Edge Function, e — crucial, dado o achado da seção 2.1 — um
jeito de essa falha aparecer para alguém. Sugestão: uma tabela append-only
`cron_invocations` que a própria chamada grava (sucesso ou falha), e o
guardrail já corrigido (seção 4.1) passa a ler dessa tabela em vez de, ou além
de, `processing_runs`.

**Opção manter GitHub Actions, mas com verificação externa** — mais barato,
mas não resolve a causa raiz (a entrega do `schedule:` continua não confiável
neste repositório, por motivo que não investiguei — pode ser característica
de repositório público, de baixa atividade, ou outra causa; **NÃO
VERIFICADO**). Precisaria de um serviço externo (ex.: um cron de terceiro,
tipo cron-job.org ou similar, chamando `workflow_dispatch` via API) como
watchdog do watchdog — adiciona uma dependência externa para resolver
dependência de um agendador que já não é confiável.

Não escolhi entre as duas. A pergunta 6.1 pede a decisão do Gabriel.

## 5. Riscos e o que esta etapa não resolve

- corrigir o guardrail (4.1) não conserta o agendador — só faz o problema
  aparecer. A causa raiz (por que o `schedule:` do GitHub Actions não dispara)
  continua sem diagnóstico definitivo nesta sessão;
- se a causa for específica deste repositório (por exemplo, um limite de
  execução do GitHub Actions para repositórios com pouca atividade recente,
  documentado como comportamento conhecido da plataforma), migrar para
  `pg_cron` resolve; se for um bug transitório da plataforma, pode se resolver
  sozinho e mascarar a necessidade de decidir isso com cuidado — não decida a
  migração só porque o problema "sumiu" sem entender por quê;
- esta frente não toca a frente A. Depois de B resolvido, A continua com a
  mesma incerteza central (A2/A3: o WhatsApp preenche `shortcutId`?) e a
  mesma lacuna de desenho (A4: a etapa 4 precisa de duas metades, não uma);
- a lacuna de deploy manual (seção 2.4) não é resolvida por nada neste plano.
  Ela é maior risco especificamente para a etapa 4, que ainda não começou.

## 6. Decisões que são do Gabriel, não minhas

**6.1 — Fonte do agendamento.**
- Opção A: migrar a consolidação para `pg_cron` dentro do Supabase. Ganha

  Supabase (menos exposta a quem tem acesso ao repositório GitHub, mais

  perde tempo — o problema já está confirmado, não é hipótese.
- Opção C: as duas coisas (pg_cron como principal, GitHub Actions como

  recente). Mais robusto, mais complexo de manter.

**6.2 — Vocabulário e horizonte da tela, com a coordenação.**
